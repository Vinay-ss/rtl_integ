# Routing demo

A small design that mirrors the picture below. Only the leaves carry
`//auto_route` annotations; the tool works out the rest.

```
                 top                      (non-ANSI, /*AUTOARG*/ style)
            ______|______
           |             |
         coreA         coreB              (ANSI AUTO-style wrappers, no hand-written ports)
        __|__         __|__
       |     |       |     |
     instC instD   instE instF            (hand-written ANSI leaves)
```

`src/leaf_c.sv` (module `leaf_c`, instance `instC`):

```verilog
input  logic  ctrl_ch,
axi_if.master data_ch);
//auto_route data_ch :: to :: instE, instF     // fan the interface out to both sinks
//auto_route ctrl_ch :: from :: instE:irq      // instE's irq output drives ctrl_ch
```

`src/leaf_d.sv`:

```verilog
//auto_route d_status :: to :: top:status_d    // expose on top's boundary as status_d
```

## Run it

```bash
./run_route_demo.sh          # Linux / macOS / Git Bash
run_route_demo.bat           # Windows
```

Both scripts copy `src/` to a throw-away `work/` directory and run:

1. `hierarchy` prints the instance tree, the file levels and the leaf-first order.
2. `route --collect-only --routes-out work/routes.toml` collects the annotations,
   resolves the instance names to exact paths and writes a reviewable `routes.toml`.
3. `route --routes work/routes.toml --dry-run` prints the planned edits as a diff.
4. `route --routes work/routes.toml --then-expand` applies them and expands every
   AUTO leaf-first.
5. The scripts print `top.v`, `core_a.sv` and `core_b.sv`.
6. The same command runs again and makes no edits.

`--relative-to filelist` resolves the paths inside `design.f` relative to the
filelist's own directory (the `-F` convention), so the demo works from any current
directory. The default, `--relative-to cwd`, resolves them relative to where you run
the command (the `-f` convention).

## What to look at

- `top.v`: an `axi_if data_ch (.clk (clk), .rst_n (rst_n));` instance appears at the
  common ancestor with its ports connected by name, and `output status_d;` is added
  as a body declaration that AUTOARG then lists.
- `core_a.sv`: gets an `axi_if.master data_ch` port. The net for the `from` route is
  named after its source port, `irq`, so the rename happens here: `instC` gets an
  explicit `.ctrl_ch (irq)` pin and coreA an explicit `input logic irq` port (a pin
  written by hand is invisible to AUTOINPUT, so the port must be explicit too).
  `instD` gets an explicit `.d_status (status_d)` pin for the same reason.
- `core_b.sv`: gets one `axi_if.slave data_ch` port feeding both `instE` and `instF`
  through AUTOINST; `irq` leaves coreB through AUTOOUTPUT and is declared at top by
  AUTOLOGIC, with no hand-written line at all on that side.
- Every inserted line carries a `// routed: <route name>` comment. Lines inside
  `// Beginning of automatic ... // End of automatics` fences are generated by the
  AUTOs, not by the router.

To start over, run the script again (it recreates `work/`).
